Test Initiative on Proxmox

This is a personal test installer in Dunky13/ProxmoxVED, branch feat/initiative. It is not an accepted Community Script. New scripts go through DevScripts first. Initiative had 173 stars on 2026-10-20, below the project's 600-star submission threshold; the fork installer was explicitly approved for personal testing.

Record test results in the personal acceptance issue.

Create the container

Run these commands as root in the Proxmox host shell, not in an existing container:

export COMMUNITY_SCRIPTS_URL=https://raw.githubusercontent.com/Dunky13/ProxmoxVED/refs/heads/feat/initiative
dev_mode=keep bash -c "$(curl -fsSL "$COMMUNITY_SCRIPTS_URL/ct/initiative.sh")"

Keep the export: the engine needs it to find the matching installer in the fork, and the container's update command remembers this source. Merely downloading ct/initiative.sh from the fork does not select the fork's install/initiative-install.sh.

The standard Community Scripts wizard creates an unprivileged Debian 13 LXC with 2 CPU cores, 2048 MiB RAM and an 8 GiB disk. Choose its bridge, storage, container ID and network settings in the wizard. These are initial test defaults, not measured capacity guarantees. Leave the OS on Debian 13: the server package requires its Python 3.13 ABI. The keep flag preserves a failed container for diagnosis. Do not add the trace flag when collecting logs containing secrets.

Open https://CONTAINER-IP, accept the self-signed certificate and create your first account immediately. That account becomes the owner. Subsequent public registration is disabled; there is no default username or password. Keep the new instance on your private network while completing this step.

What it installs

  • The official initiative-server Debian release package, after checking its matching architecture-specific SHA-256 manifest. It does not install the Electron desktop client or rebuild the Python/browser dependencies.
  • PostgreSQL 17 from Debian's repository, with a generated database password.
  • The package's initiative-server.service, running as the package's unprivileged initiative account.
  • Nginx on HTTPS port 443, with HTTP port 80 redirected to HTTPS and WebSocket proxying. Initiative listens on loopback port 8173. HTTPS is needed by browser crypto features even when accessing the application by LAN address.

The installer uses Community Scripts' setup, release, certificate and nginx helpers. The native package already contains its Python environment, so there is no setup_uv, pip or Node.js install. The database owner has the privileges needed for initial RLS-role provisioning and the LEAKPROOF search operator. Initiative disposes of that bootstrap connection before serving requests and uses its separate application roles for runtime access.

Configuration and updates

Configuration and generated secrets live in /etc/initiative/server.env, owned by root:initiative, mode 0640. Uploads live in /var/lib/initiative/uploads. Preserve SECRET_KEY: it also protects encrypted data. The installer refuses to overwrite an existing configuration.

After changing the IP or using a domain, update APP_URL in the configuration and run:

systemctl restart initiative-server

Use a trusted HTTPS reverse proxy and certificate for a public domain. The self-signed certificate is created for the container's original address.

Take a Proxmox backup before upgrading. Then run inside the container:

update

The updater checks for a newer release, downloads and verifies it before stopping anything, then stops Initiative and PostgreSQL. It copies the local configuration, uploads, PostgreSQL configuration and stopped database cluster, including roles, into a private /opt/initiative-backup.* directory. It starts PostgreSQL, installs the verified package with existing configuration preserved, and explicitly starts Initiative. Readiness must pass before the installed-version record moves forward. Backup directories remain for manual recovery and consume disk space.

This backup covers the installer's default local paths. If you move storage or use an external database, arrange matching backups separately. A failed update can leave services stopped. Inspect its error and backup before retrying. Do not start an older package against a migrated database: restore a matching backup or the whole Proxmox container instead. Do not blindly rerun the installer.

Check the result

Inside the new container:

systemctl is-active initiative-server nginx postgresql
curl --fail http://127.0.0.1:8173/api/v1/readyz
curl --insecure --fail https://127.0.0.1/api/v1/readyz

Expected: all three services are active and both readiness responses report "status":"ok", with every check "ok". --insecure is only used here to probe the local self-signed HTTPS endpoint.

For a failed start:

systemctl status initiative-server nginx postgresql --no-pager
journalctl -u initiative-server -n 100 --no-pager

Do not paste server.env, database passwords or account credentials into an issue or chat.

Real Proxmox acceptance still needs these checks:

  1. Create an unprivileged Debian 13 container through the wizard on your host.
  2. Open HTTPS from your browser and create the first owner account.
  3. Create a community, initiative, project and task; upload a file and exercise live document editing. Confirm a second public registration is rejected.
  4. Reboot the container and confirm the app, task and upload remain available.
  5. Run update. A current installation should leave services and data alone. When another server release is available, verify the upgrade and backup, then recheck your task, upload and login.

Validation and handoff

Local validation commands, from the fork checkout:

bash -n ct/initiative.sh install/initiative-install.sh tools/tests/initiative-test.sh
shellcheck -e SC1090,SC1091,SC2154 ct/initiative.sh install/initiative-install.sh tools/tests/initiative-test.sh
bash tools/tests/initiative-test.sh
jq -e . json/initiative.json
git diff --check

The ShellCheck exclusions cover dynamic framework imports and variables supplied by Community Scripts. All 15 regression scenarios passed. The harness runs without root or network access; it verifies checksum rejection, server-versus- desktop package selection, the architecture and OS guards, missing assets, unavailable or partially failed readiness, failed backups, a still-running database, current-version no-op behavior and successful install/update ordering.

A disposable Debian 13 arm64 VM also passed these checks using Initiative v0.76.0 and the real shared core helpers:

  • Release asset download and SHA-256 verification, native package installation, PostgreSQL bootstrap, nginx HTTPS and systemd service activation as initiative.
  • First-owner registration with public registration disabled, login, rejection of subsequent public registration, community/initiative/project/task creation, SPA delivery and the signed native update manifest.
  • Reapplying the same release through the updater after setting an older version marker: offline database-cluster backup, correct backup permissions, restart, unchanged configuration and upload checksums, and preserved login/task data.
  • A second update on the current version performed no service restart.

The guest harness supplied the framework's environment and replaced the host wizard, container provisioning, OS-update, resource-check and MOTD/cleanup steps. Application installation and updater commands used real services and packages. The cached-release skip found by this test was corrected by forcing downloads into each fresh staging directory. The database shutdown check also required stopping Debian's postgresql@17-main cluster unit explicitly.

Native validation used core commit 1ed248530539400a584892d9930b97cd9b823b92, against DevScripts base 2484a382cafe659ff63ffcf656a4e75f79975c02. Development logs are local evidence, not hosted CI artifacts. No Proxmox host was changed by this development session; the Proxmox wizard, LXC-specific behavior, amd64 runtime, browser interactions and a genuine upgrade across two published versions remain operator acceptance work.
